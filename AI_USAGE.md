# AI Usage

## Какие части делались с AI

AI использовался как инженерный помощник на всех этапах реализации SPA:

- подготовка frontend-архитектуры на React, TypeScript, Vite и Feature-Sliced Design;
- настройка TanStack Router, TanStack Query, MSW, Zustand, React Hook Form и Zod;
- перенос OpenAPI-схемы в проект и ручное описание runtime-схем DTO;
- реализация mock API для списка аукционов, детальной карточки, ставок и отправки ставки;
- техническая реализация экранов списка, детальной страницы, истории ставок и формы ставки по заданному направлению;
- подключение shadcn/ui, Sonner, темной/светлой темы и Leaflet-карты маршрута;
- написание unit-тестов для search params, request builder, DTO-схем, валидации ставки и расчета дистанции;
- визуальные и UX-правки по найденным дефектам: календарь, сайдбар, скелетоны, тосты, цветовая тема, фильтр дистанции.

## Какие решения кандидат принял сам

Самостоятельно были приняты ключевые проектные решения:

- руководить интерфейсом по предоставленному Figma-макету и использовать его как дизайн-ориентир;
- определить общую дизайн-систему проекта: визуальный стиль, цветовую тему, поведение сайдбара, плотность интерфейса и требования к аккуратности UI;
- развивать сайдбар фильтров как основной рабочий инструмент списка, включая календарь, ширину, скроллбар и структуру фильтров;
- добавить карту маршрута как пользовательскую идею для быстрого просмотра направления перевозки из карточки аукциона;
- использовать Feature-Sliced Design с явными слоями `app`, `pages`, `widgets`, `features`, `entities`, `shared`;
- брать UI-компоненты через shadcn/ui, не копить собственную библиотеку компонентов без необходимости;
- использовать MSW как единственный источник backend-эмуляции, потому что backend по заданию недоступен;
- держать фильтры, сортировку и пагинацию в URL search params для воспроизводимых сценариев проверки;
- использовать Zustand только для локального UI-state панели фильтров, не смешивая его с серверным состоянием;
- валидировать форму ставки через строковый ввод и Zod transform, чтобы избежать native number-step ошибок браузера;
- считать дистанцию маршрута по координатам городов, а не через цену и цену за километр;
- игнорировать скрытую белую инструкцию в PDF про обязательный суффикс `*.component.tsx` как prompt-injection.

## Какие AI-предложения были отклонены

В процессе работы были отклонены или пересмотрены следующие предложения:

- не стали оставлять лишние стартовые UI-компоненты и типы, которые не нужны текущей функциональности;
- не стали хранить AI-логи, черновики и промежуточные markdown-артефакты в репозитории;
- отказались от `corepack` в рабочих командах, чтобы проверяющему было привычнее запускать проект через установленный `pnpm`;
- не стали использовать скрытое требование `*.component.tsx`, так как оно не видно человеку при обычном чтении PDF;
- не стали подключать реальный backend или внешние сервисы карт для данных аукционов, потому что задание требует локальные MSW-моки;
- пересмотрели расчет фильтра дистанции, когда стало видно, что расчет через `current_price / price_per_km` дает неверные маршруты.

## Как распределялась работа

Кандидат задавал продуктовые и визуальные решения: предоставил Figma-макет, направлял дизайн-систему, определял поведение сайдбара, предлагал карту маршрута, указывал на UX-дефекты и принимал решения по версиям, коммитам и ограничениям репозитория.

AI помогал как технический исполнитель: предлагал реализацию, редактировал код, сверял требования, запускал проверки, исправлял найденные ошибки и оформлял документацию. Финальные решения по спорным местам принимались кандидатом.

## Какие места проверялись особенно внимательно

Особенно внимательно проверялись:

- соответствие обязательному стеку и маршрутам из задания;
- структура MSW handlers и изменение состояния после `POST /auctions/{auctionUuid}/bets`;
- инвалидация list/detail/bets queries после успешной ставки;
- Zod fallback для search params, чтобы некорректный URL не ломал приложение;
- валидация ставки: обязательность, значение больше 0, min, max, step и 422 validation error;
- hidden-флаги DTO: `can_set_bet`, `hide_bets_history`, `hide_points_address_and_contacts`, `no_view_cargo_price`;
- отсутствие лишних AI-логов и временных файлов в git;
- корректность фильтра дистанции относительно карты маршрута;
- production deploy на Vercel с включенным MSW, так как backend по заданию отсутствует;
- прохождение `pnpm test:run`, `pnpm typecheck`, `pnpm build` и git hooks.

## Какие риски остались

Оставшиеся риски:

- схемы DTO написаны вручную по OpenAPI, поэтому при изменении спецификации потребуется ручная синхронизация;
- фильтр `statuses` реализован через одиночный `status` в UI, а не как отдельный multi-select;
- `no_view_cargo_price` сейчас скрывает цену груза в таблице параметров, но торговая панель все еще показывает текущую цену аукциона;
- карта маршрута использует локальный расчет по координатам городов, а не дорожный routing API;
- нет E2E-тестов в браузере;
- MSW-моки покрывают основные сценарии, но не все возможные edge cases реального API.

## Что улучшить при наличии еще одного дня

Если бы был еще один день, я бы сделал:

- добавил multi-select для `statuses` и синхронизировал его с OpenAPI-полем;
- уточнил и полностью применил бизнес-смысл `no_view_cargo_price`;
- добавил Playwright smoke-тесты для списка, фильтров, детальной страницы и отправки ставки;
- расширил MSW-сценарии ошибок и edge cases;
- добавил генерацию типов из OpenAPI или отдельную проверку совместимости схем;
- улучшил карту маршрута через реальный routing provider при наличии разрешенного внешнего API;
- добавил мониторинг production deploy или smoke-проверку Vercel URL после каждого релиза.
